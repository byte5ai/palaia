# SPEC-505: v2 sunset

## Goal
MASTERPLAN §11 / roadmap: v2 users get a clear, kind path to v3 — v2 stays
installable and hotfix-able, nobody is stranded, and every v2 surface
points forward.

## Deliverables — mind the two-track rules
The hard separation rules (AGENTS.md) still bind: the ONLY v2-root change
allowed on `main` is the intentional top-level cross-reference. Everything
deeper targets the **`v2-maintenance`** branch as its own PR.

1. On `main` (this SPEC's branch): the top-level `README.md` gains the v3
   launch pointer + sunset statement (v2 = maintenance-only, hotfixes via
   `v2-maintenance`, link to the migration guide). This is the sanctioned
   cross-reference, nothing else at root changes.
2. `v3/docs/migrate-from-v2.md`: the complete migration guide — what
   carries over (memories via `palaia-hub import v2`, with the real
   command), what changes (per-client reconnect, tokens are new, UI moves
   to the hub), what does not exist yet in v3 (be honest — audit v2's
   feature surface against v3 and LIST the gaps rather than hand-waving),
   rollback story (v2 store is never modified by the importer — verify and
   state it). Linked from the docs site (SPEC-503 nav slot exists).
3. A **separate PR to `v2-maintenance`** (same branch protocol, base
   `v2-maintenance`): v2's README banner (maintenance status + migration
   link), a deprecation notice in v2's CLI startup (one line, not a nag —
   shown at most once per day, stored marker), and v2's SKILL.md copies
   gain the pointer. No functional v2 changes.
4. Timeline statement (owner decides dates; the SPEC ships the structure):
   the sunset section states support policy in terms of the owner's
   choosing — template with clearly marked decision points, flagged in the
   PR for the owner to fill.

## Acceptance criteria
- [ ] main-branch PR touches ONLY the top-level README (+ v3/ files) —
      verified by the diff itself
- [ ] migration guide's import command round-trips a real v2 fixture store
      (reuse SPEC-111's golden fixtures; test)
- [ ] v2 gap list is generated by comparison, not memory: enumerate v2's
      documented commands/features and mark each carried/changed/missing
- [ ] v2-maintenance PR: banner + once-per-day notice, tests green on that
      branch's own suite
- [ ] jargon lint on all new prose

## Non-goals
Removing or archiving any v2 code; setting sunset dates (owner's call);
migrating OpenClaw (v2 continues to serve it, MASTERPLAN §6).
